# Giovanni Knowledge Layer — living constitution + indexed canon

Knowledge is **canonical state** — facts and operating principles that an AI Chief of Staff treats as authoritative when memory and knowledge disagree. It is not a wiki, not a chat log, not a personal note pile. Knowledge is the source of truth.

Memory is volatile. Briefs go stale. Decisions get superseded. Knowledge stays as the single document set anyone can grep to find out "how does this domain actually work?". When the constitution and any other doc disagree, the constitution wins.

This document explains the layer's contract, when to add a knowledge doc, how to amend the constitution safely, and how the auto-generated index stays current.

---

## Layer contract

| File | Status | Owner |
|---|---|---|
| `knowledge/<constitution>.md` | Single source of truth — living document. One per fork. | Principal (only the principal amends; specialist agents propose patches). |
| `knowledge/INDEX.md` | Auto-generated index of every knowledge doc. | Regen script. Never edit by hand. |
| `knowledge/*.md` (other) | Indexed canonical documents. Architecture references, country setups, contract terms, operating playbooks. | Principal + named domain experts. |
| `knowledge/*.{xlsx,html,pdf,...}` | Indexed canonical data files. Listed in INDEX, content not parsed. | Principal. |
| `knowledge/archive/` | Superseded canonical docs. Read-rarely, kept for historical context. Not indexed. | Principal — moves docs here when superseded. |

**Mandatory minimum for a fork:** one constitution file. Everything else is opt-in.

## Knowledge vs memory — the binding split

| Question | Goes to |
|---|---|
| Is this an **operating principle** that should hold across months? ("We never sell without a finance team in the room.") | Constitution patch — knowledge. |
| Is this an **architectural decision** with reasoning, alternatives, and supersession rules? | Constitution patch — knowledge. Decision record is the audit trail (memory); the resulting canonical fact is knowledge. |
| Is this a **transient blocker** I'm tracking right now? | Memory L1 — `memory/CLAUDE_MEMORY.md`. |
| Is this a **per-event prep note** for a meeting tomorrow? | Memory L3 — `memory/briefs/`. |
| Is this a **person-tied profile** with sentiment trajectory? | Memory L3 — `memory/stakeholders/`. |

**Test:** if a different agent / colleague six months from now needs this to be true and unambiguous, it's knowledge. If it's only useful for the next 30 days, it's memory.

## The living constitution pattern

One file per fork holds the canonical operating principles, architecture decisions, organizational facts, and decision audit trail back-links. Source convention is `<DOMAIN>_ustava.md` (Czech for "constitution"); Giovanni's generic template is `knowledge/constitution.template.md`.

### Structural conventions

The template (`knowledge/constitution.template.md`) encodes a binding shape. Sections use this rhythm:

1. **Frontmatter** — version, last review date, status of document as a whole.
2. **Table of contents** — anchor IDs (auto-generated by the script or hand-maintained; see template).
3. **Sections** — each section anchored, each has a status badge (`RESOLVED` / `OPEN` / `SUPERSEDED`).
4. **Factoid-vs-reasoning layout per section** — `FACT (source: <citation>)` lines separate from `REASONING / IMPLIES` blocks. An agent reading the section can grab the facts without re-deriving the reasoning every time.
5. **Supersedes pointer** — when a section replaces a prior position, the old anchor is preserved with `SUPERSEDED → §<new-anchor>` pointer rather than deleted.
6. **Back-links to decision records** — sections cite the `memory/decisions/<YYYY-MM-DD>-<slug>.md` that established the position.

### Status badges (binding)

| Badge | Meaning |
|---|---|
| `RESOLVED` | Position settled; should hold unless a `trigger condition` from the decision record fires. |
| `OPEN` | Active question; section captures the current best understanding, expected to change. |
| `SUPERSEDED → §<anchor>` | Position retired; reader should follow the pointer to the active section. |
| `DRAFT` | Section under construction; not yet authoritative. Should not be referenced by other sections until promoted to `RESOLVED` or `OPEN`. |

### Commit-traceability requirement

Every amendment to the constitution must:

1. **Use the `docs(constitution):` commit prefix** (or `decision: <slug>` if the constitution change is the artifact of a decision being recorded in memory).
2. **Cite the trigger** in the commit body — what changed (new information, decision record, supersession of prior position).
3. **Update the section's last-touch date** in the constitution itself.
4. **Move the prior section to a `SUPERSEDED →` stub** if the change is a replacement, not an addendum.
5. **Update the table of contents** if section IDs changed.

The `post-constitution-edit-check.sh` hook flags missing supersedes-pointers and missing commit-message prefix.

### How to amend safely

When you're about to edit the constitution:

1. **Decide if this is an amendment or a supersession.** Amendment = adding to a section. Supersession = replacing a section's claim with a different one.
2. **For supersessions**: rename the old section header to `<old name> (SUPERSEDED → §<new-anchor>)` and leave a one-paragraph stub explaining why the position changed. Do not delete — the old position is historical record.
3. **Cite the decision record.** Most constitution amendments derive from a decision recorded in `memory/decisions/`. Add `Source: memory/decisions/<file>` line at the bottom of the new section.
4. **Update last-touch date.** Add a date marker (e.g. `_Last updated 2026-05-21._`) so age can be tracked.
5. **Commit with `docs(constitution):` prefix.** Body should explain what + why.

### Anti-patterns

- **Editing the constitution to reflect ambition rather than reality.** The constitution is a record of what *is* and what is *decided*, not what you hope. If a position isn't decided yet, leave it `OPEN`.
- **Deleting superseded content.** Always preserve the old section as a stub with a pointer. Future readers need the trail.
- **Cramming current operational state into the constitution.** That's memory's job. Constitution is canonical; memory is current.
- **Adding sections without anchor IDs.** Anchors enable inbound pointers from memory and other constitution sections. No anchor = unlinkable = lost.

## INDEX auto-regen

`knowledge/INDEX.md` is regenerated by `scripts/build-knowledge-index.sh` on every Edit/Write to any `knowledge/` file (except INDEX itself). The hook lives at `.claude/hooks/post-knowledge-edit.sh`.

### What INDEX contains

- One row per `knowledge/*.md` file (excluding INDEX.md and README.md).
- One-liner extracted from the file's first H1 (or first non-blank line if no H1).
- Last commit date (from `git log -1`).
- File size (human-readable).
- Separate section for non-markdown data files (xlsx, html, pdf).
- Archive directory listed as count-only.
- Cross-references footer pointing to memory + agent instructions.

### When INDEX gets stale

- You edited a knowledge file but did not re-run the regen script (and the hook didn't fire because you edited via a non-hook-aware tool).
- You added a new file that needs to be linked from the cross-references footer.
- The regen template itself changed.

The `lint.sh` rule `index-stale` checks for this — runs `build-knowledge-index.sh --dry` and diffs against the committed INDEX.md. CI / pre-commit catches drift.

### Never edit INDEX by hand

Any manual edit is overwritten on the next knowledge edit. If you want to change the INDEX format (column ordering, cross-reference text, archive treatment), edit `scripts/build-knowledge-index.sh`, then re-regen.

## When to add a knowledge doc

Beyond the constitution, additional knowledge docs are useful when:

- **The constitution would balloon.** If a section grows past ~200 lines, extract to its own knowledge file and leave a one-paragraph summary + pointer in the constitution.
- **The doc is reference material** (architecture diagrams, country setups, contract templates, glossaries). The constitution cites it; the doc is the detail.
- **The doc is a snapshot of an external source** that you need a stable mirror of (financial model from spreadsheet, third-party API reference, regulatory text excerpt).

**Do not** add a knowledge doc for:
- A meeting summary (that's `memory/briefs/` or `memory/archive/`).
- A draft you haven't finalized (`deliverables/draft/` outside knowledge).
- Personal notes about a stakeholder (`memory/stakeholders/`).

## Archive convention

When a knowledge doc is superseded:

1. **Move to `knowledge/archive/<filename>`** (preserve the file, do not delete).
2. **Add to git in same commit as the supersession** so history is clean.
3. **Update any inbound pointers** in the constitution and other knowledge docs.
4. **INDEX regen lists `archive/` as count-only** — superseded docs are not browse-friendly, only audit-friendly.

For older quarterly retirement: archived knowledge docs that have been untouched for >12 months can move to `knowledge/archive/<YYYY-Q?>/<filename>` for further organization, but this is optional.

## Cross-architect dependencies

Knowledge layer alone is the canonical store. Adjacent architects own the surrounding mechanics:

- **Memory layer** (operational state, decision audit trail) → `memory-architect`.
- **Constitution amendment workflows** (when does an amendment need adversarial review? how do we propose patches?) → covered by `docs/governance.md` + adjacent architects (`adversarial-architect`).
- **Decision record schema** (the audit trail back-linked from constitution sections) → `memory-architect`.

When forking Giovanni for a new domain, the knowledge layer is mandatory. The constitution is the first artifact to fill in — see `knowledge/constitution.template.md`.
